# AI 连接修复与前端性能优化方案

验证日期：2026-10-01。入口：<http://localhost:8080/>。

## 已完成的 AI 修复

`server/.env` 中的 `AI_MODEL` 原来是模板文字“服务商支持的模型名称”。密钥通过 Moonshot 模型列表接口验证后，将模型名改为实际可用的 `kimi-k2.6`。保留原密钥。

真实网页请求还出现过一次 60 秒超时。直接调用实测：默认思考模式的结构化请求约 22—33 秒；关闭思考模式约 6.7 秒。该对比为少量请求的结果，不代表稳定延迟保证。

后端新增可选配置 `AI_OPENAI_THINKING`：空值不发送额外参数；`enabled` / `disabled` 发送 `thinking.type`。当前 Moonshot 配置使用 `disabled`。其他 OpenAI 兼容服务只有明确支持该参数时才填写，Anthropic 不受此项影响。

当前非密钥配置：

```dotenv
AI_PROVIDER=openai
AI_ENDPOINT=https://api.moonshot.cn/v1
AI_MODEL=kimi-k2.6
AI_STRUCTURED_OUTPUT=true
AI_OPENAI_THINKING=disabled
```

服务已重启。65 个后端测试全部通过。真实模型网页验证通过：许愿池提交后即开始生成，后端约 6.8 秒返回完整结果；正殿显示总结，菩提树显示五项详细内容，保存后状态为 `complete`，没有调用 `/choice`，没有页面脚本异常。也检查了 390×844 下详细卡片的滚动和保存入口。

证据：`tools/e2e/live-ai.audit.json`、`live-summary.png`、`live-detail.png`，以及 `tools/frontend/backend-ai-fixed.log`。不包含 API 密钥。网页测试使用章节导航进入许愿池，未将山门到香炉的开场动画作为 AI 测试范围。

## 待实施的视觉方案

此轮没有修改前端视觉实现，也没有进行用户设备的帧率量化。以下区分源码事实、用户反馈和待验证原因。新增问题仅加入待解决清单，尚未实施或验证。

| 问题 | 现象与核查状态 | 解决方案 |
| --- | --- | --- |
| 鼠标跟随不顺畅 | `unified-cursor.js` 在每次 `pointermove` 中更新 `left/top` 和样式；父页面与 iframe 各有独立手形元素；还对整个页面子树的 DOM 变化执行 iframe 扫描 | 事件只记录最新坐标，由 `requestAnimationFrame` 每帧用 `translate3d` 更新；仅在姿态改变时切换图片/类；预解码小尺寸光标素材；缩小观察器范围并清理旧页面监听 |
| 香炉点击后固定手残留 | 父页面和香炉 iframe 各自创建 `.unified-hand`；在父页面遮罩仍显示的路径中复现了两只手，父页面手停在旧坐标。跳过序章后的直接章节进入未复现同样残留，用户所述的首次点击路径仍需进一步复核 | 统一管理光标的活动页面；进入子页面、打开/关闭地图、页面跳转时隐藏其他页面手形并清除按压状态；确保同时最多一只光标可见。保留仪式画面中的实体手部素材 |
| 过渡卡顿 | `courtyard-passage.js` 一次创建 122 张图片，约 23.7 MiB 文件；首帧实测 1664×928，同尺寸 122 帧全部解码的像素数据约 719 MiB，实际内存取决于浏览器；每次滚轮事件直接换图，没有等待目标帧解码 | 先解码首帧，预取当前帧前后少量帧并限制缓存；每帧最多更新一次画面；目标图未准备好时保留当前帧；连续单向动画可评估视频播放，往返滚动先保留图片序列 |
| 过渡和背景发糊 | 正殿弹层有 `backdrop-filter: blur(3px)`，签筒背景有 `blur(1px)`；石径素材低于部分高分辨率屏幕；场景存在缩放和整层滤镜 | 分别检查素材放大、滤镜和动画重采样；避免整层模糊动画，改用透明度叠层；需要清晰的阅读背景可减弱或移除弹层背景模糊；高分辨率素材按显示尺寸分档加载 |
| 序章字体和大小 | 用户反馈序章字体、字号需要调整；具体字号和移动端效果待核查 | 统一序章字体、字号层级、行距与文本宽度，分别检查桌面和手机的可读性及画面比例 |
| 叩门之后的过渡 | 用户反馈叩门后的动画衔接需要优化；具体卡顿、跳变和等待位置待复现 | 单独检查叩门结束、开门、入殿的衔接；提前准备下一场景，统一过渡节奏，确保上一段完成后再进入下一段 |
| 四大天王后面两个标签挡住诗句 | 用户反馈存在标签与诗句遮挡，具体两个标签及不同屏幕下的重叠范围待定位 | 调整标签位置、文字区域和显示时机，为诗句留出固定阅读空间；检查四段诗句及桌面、手机布局，避免遮挡 |
| 上香之后白光卡顿 | 用户反馈上香结束后的白光过渡卡顿；白光动画与下一页面加载是否重叠待检查 | 将白光过渡作为独立性能检查点；提前准备许愿池，减少大面积滤镜和重复动画，在遮罩覆盖时切换场景，准备完成后再揭开 |
| 许愿池、无问殿与后续页面样式不一致 | 按用户描述记录涉及页面；具体路由和差异待逐页核对 | 统一字体、标题层级、按钮、提示、卡片、间距及过渡语言；在统一规则下保留各场景的主题差异 |
| 全流程交互方式统一：点击或滑动 | 用户提出统一交互方式，并指出点击更利于动画过渡；最终方式尚未确定 | 优先评估以点击触发完整动画的方案，统一前进动作、提示和完成条件；对确需滑动的环节单独评估。确定规则后同步调整全流程，避免同一动作在不同章节使用不同操作 |

建议先确定全流程的主要交互方式，作为动画衔接的共同规则；随后统一光标并修复跨页面残留，同时处理序章排版和标签遮挡；再优化叩门、石径、上香白光等过渡，最后统一各页面样式与清晰度。光标问题与过渡解码共同占用主线程，适合一起做性能检查。

验收：完整流程中快速移动、点击、拖动、打开/关闭地图和切换章节始终只有一只光标；按压姿态不会卡住；序章文字清晰易读，四大天王标签不遮挡任何诗句；叩门和上香白光衔接不跳帧、不闪空白；主要交互方式及提示一致；许愿池、无问殿与后续页面遵循同一套样式规则；记录目标设备的帧时间、长任务及缓存峰值，若保留滚动则连续滚动不出现未解码空帧；保持现有仪式、许愿和两层输出流程。
