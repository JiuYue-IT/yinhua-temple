# 仓库操作指南

仓库：<https://github.com/JiuYue-IT/yinhua-temple>。下面命令使用 PowerShell，在项目根目录执行；已经克隆仓库的成员从“每次开发”开始。

## 分支约定

| 分支 | 用途 | 更新方式 |
| --- | --- | --- |
| `main` | 稳定、可运行的版本 | 从 `develop` 提 PR，检查后合并 |
| `develop` | 团队开发集成版本 | 从个人工作分支提 PR，检查后合并 |
| `feat/具体功能`、`fix/具体问题`、`docs/具体文档` | 一项具体任务 | 从最新 `develop` 创建，提交后推送到 GitHub |

每次新任务都创建一个新分支。工作流程：**更新 develop → 创建新分支 → 修改和验证 → 提交 → 推送新分支 → 提 PR 到 develop → 检查与处理反馈 → 合并**。

`main` 和 `develop` 使用分支保护：通过 PR 更新，要求 GitHub Actions 的 `test` 检查通过、分支与目标保持同步、PR 讨论全部解决，禁止强推和删除。仓库管理员也遵循保护规则。当前不强制固定数量的 Approve；团队应由了解该部分代码的成员检查后再合并。

## 成员权限

普通开发成员使用 **Write**：可以克隆、创建和推送工作分支、提交和审查 PR，并在保护规则满足后合并 PR。仓库设置、权限管理由所有者负责。

## 第一次下载和运行

安装 Git 和 JDK 17。克隆后切换到团队开发分支：

```powershell
git clone https://github.com/JiuYue-IT/yinhua-temple.git
Set-Location yinhua-temple
git switch develop
```

首次使用 Git 时设置自己的提交身份：

```powershell
git config user.name "你的名字"
git config user.email "你的 GitHub 邮箱或 GitHub 提供的隐私邮箱"
```

按照 [README](../README.md) 配置本地 `server/.env` 并启动。完整入口是 <http://localhost:8080/>。自己的 API Key 只放本地，不能提交。配置、测试和素材要求见 [参与开发](../CONTRIBUTING.md)。

## 每次开发：先更新，再创建新分支

先执行 `git status`，确认上一项工作已提交或妥善保存。不要在未保存修改时直接切换任务。

```powershell
git status
git switch develop
git pull --ff-only origin develop
git switch -c fix/cursor-performance
```

`fix/cursor-performance` 是示例名称，每次换成当前任务的名称。不要在 `main`、`develop` 上直接编写和推送新内容。

## 提交并把新分支推到 GitHub

修改后先按 [参与开发](../CONTRIBUTING.md) 完成相关验证，再查看差异。只添加这次需要提交的文件；下面以修改待办为例：

```powershell
git status
git diff
git add -- 'docs/10-待办.md'
git diff --cached
git commit -m "文档：更新待办进度"
git push -u origin fix/cursor-performance
```

实际使用时，将文件路径、提交说明和分支名替换为自己的任务。新增、删除或重命名文件也要加入暂存区；删除/重命名时明确添加涉及的旧路径与新路径。后续在同一分支继续修改，重新 `git add`、`git commit`，然后执行 `git push`，PR 会自动更新。

不要提交 `.env`、密钥、个人配置、`archive/`、日志、`node_modules` 和构建产物。不使用强制推送来解决普通协作问题。

## 在 GitHub 提 PR 到 develop

1. 推送成功后打开仓库，点击 **Compare & pull request**；也可进入 **Pull requests → New pull request**。
2. 确认 **base: develop**，**compare: 你的工作分支**。日常任务不要误选 `main`。
3. 填写标题，以及修改目的、影响范围、验证结果和未验证内容；视觉修改附前后截图。
4. 点击 **Create pull request**，请相关模块成员查看差异。
5. 等待 Actions 检查通过，处理反馈与冲突。自动测试通过不能代替动画、交互和手机布局的人工检查。
6. 没有未解决问题后，点击 **Merge pull request → Confirm merge**。可以保留默认合并提交，避免丢失分支提交历史。
7. 合并成功后可以删除这次工作分支；下一项任务重新从最新 `develop` 创建。

合并按钮不可用时，先看 PR 页面提示：检查失败、分支过期或冲突需要先处理，不要绕过保护规则。

## 分支过期或出现冲突

在自己的工作分支中，先保存并提交当前修改，再合入最新 `develop`：

```powershell
git fetch origin
git merge origin/develop
```

若出现冲突，逐个核对冲突文件，和相关成员确认正确内容，清除冲突标记后，只暂存已解决的文件，再执行 `git commit` 和 `git push`。如果暂时无法正确解决，可执行 `git merge --abort` 返回合并前状态，然后请相关成员协助。不要用“全部采用我的版本”覆盖其他人的修改。

## 合并后开始下一项任务

```powershell
git switch develop
git pull --ff-only origin develop
git switch -c feat/next-task
```

旧工作分支只在确认已合并且无需保留后删除。不要删除 `main`、`develop` 或其他成员的工作分支。

## 将稳定版本合入 main

当 `develop` 中的功能完成集成验证后，在 GitHub 新建 **base: main / compare: develop** 的 PR。说明本次发布内容，等待 `test` 检查并确认完整流程可运行，检查后合并。不要在合并后删除 `develop`。

如果 PR 提示 `develop` 落后于 `main`，通过工作分支将最新 `main` 合入，再提 PR 更新 `develop`；不要直接推送到受保护分支。
